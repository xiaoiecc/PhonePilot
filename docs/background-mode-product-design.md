# 后台操控：用户流程与进度呈现

日期：2026-11-08。状态：产品设计基线，已接入 1.0.3 候选版；实际范围见 [验证记录](capsule-background-validation-20261108.md)。

来源：用户要求后台运行时显示类似灵动岛的悬浮胶囊，点击可将当前目标应用带到前台，并可在同一次任务中切回后台；同时讨论加强模型的中途输出。

本设计扩展 [悬浮窗交互方案](overlay-interaction-design.md)，执行边界仍遵守 [架构契约](architecture-contract.md) 和 [后台技术方案](background-execution-technical-design.md)。产品目标不能替代能力验证。当前原型验证的是部分应用链路、坐标输入和正常退出任务迁移；不是所有 App 的防抢屏证明，后台无障碍、输入法与双向运行中迁移仍需验收。

## 1. 用户所理解的模式

- **前台操控**：AI 使用当前目标应用的主屏界面。用户可以看到操作过程。
- **不打扰模式**：AI 在后台显示空间中操作目标应用，用户继续使用主屏。
- **暂停**：AI 不执行下一步，页面、对话和任务继续保留。

执行位置与暂停是两个不同维度：前台/后台都可以暂停，也都可在具备能力后继续执行。切换位置不新建会话、不重跑用户指令、不重放旧动作。

用户无需知道 Display ID、任务容器或截图后端。运行中显示的是已经确认的实际位置；偏好设置只决定新任务的默认位置。

## 2. 后台悬浮胶囊

胶囊显示目标应用、简短进度、暂停和停止。胶囊主体具有明确的“切到前台”语义，图标与无障碍描述标明这一点；独立暂停/停止按钮的点击不能冒泡成迁移。

示例内容：`QQ · 正在查找项目群`。进度来自模型简短说明与真实执行阶段，不只显示工具内部名称。

用户点击主体后，将**当前登记、确认归属的目标任务**带到主屏；不是重新点 Launcher 打开一个新实例。详情入口单独提供，避免同一次点击既打开详情又切换执行位置。小球点击先展开胶囊，不立刻迁移应用。

用户已明确：点击胶囊切到前台是为了观看 Agent 接着一步步操作，**切换本身不触发用户暂停或人工接管**。正在运行的任务在迁移和重新观察完成后继续运行；原本已暂停的任务仍保持暂停。暂停与人工接管是独立操作，不能混在“切到前台”里。

## 3. 前后台来回切换

前台卡片提供“转后台”；后台胶囊主体提供“切到前台”。主 Chat 的任务状态区提供同样入口，它们转发同一命令。

对用户的表现：

1. 点击后即时显示“正在切换”，短暂禁用重复切换，停止仍可用。
2. 等当前设备操作退出安全边界，再迁移目标任务，期间不注入新动作。
3. 验证真实落点和新目标可操作性后才更新模式标记。
4. 原来已暂停的任务继续暂停；切换自身不能清掉用户暂停、草稿或人工交互。
5. 两个方向遵循同一规则：切换前运行，切换成功后继续原任务；切换前已暂停，成功后仍暂停。迁移期间的短暂操作门禁不是用户暂停，不要求额外点击继续。切换中新增的暂停、停止或人工交互优先，不能被迁移成功回执清除。
6. 切换使旧截图、节点引用及正在生成但绑定旧观察的操作失效；重新观察后生成后续动作，不能把旧坐标直接换一个 display 执行。

模式变化必须告知 runner，使模型知道输入目标已变化；不能只换底层 displayId、保留旧计划继续点。必要时取消旧观察对应的在途请求，保留未完成工具批次不能直接重用的约束。

转后台后，不为了还原桌面额外发 HOME 或重新打开之前应用。优先让系统自然显露后方任务；若用户已经切到其他页面，不把旧的前台页面强行恢复过来。

同包不同任务、系统设置页和其他关联应用都按真实任务归属处理。不能按包名搬走用户自己的实例；默认只搬当前任务，关联任务如何归还由后端明确登记，不能扫描所有同包任务后一起迁移。

## 4. 失败与人工接管

| 场景 | 用户体验 |
| --- | --- |
| 切换失败且原位置已确认 | 保持原位置并暂停，提示原因，允许明确重试 |
| 部分迁移或实际落点不确定 | 显示“切换未完成，已暂停”，提供恢复/停止；不猜位置继续执行 |
| 后台目标跳回主屏 | 若能可靠检测，暂停并告知；不能谎称仍在后台，也不自动反复抢回任务 |
| 需要用户确认 | 胶囊提示需要确认，展开同一人工交互；打开卡片不代替确认 |
| 需要手动操作目标应用 | 明确提供“切到前台接管”，暂停后交接，用户完成后才能继续 |
| 用户暂停后补充指令 | 输入区从一行随排版增高，到上限才滚动；发送被接受后按既定规则继续 |
| Shizuku 断连 | 保留对话与任务信息，显示原因，不静默降级为主屏操控 |

暂停、切换、接管、查看详情和输入不创建多个运行 Job。停止优先于迟到的切换回执，旧回执不能使已结束任务复活。

## 5. 结束与不打扰原则

后台完成不自动打开目标应用或主 App。简短完成提示提供“查看结果”；只有用户选择才打开。目标应用按技术方案迁回主屏后台，遵循应用自己的最近任务标记。

结束前仍有任务归还或资源清理时显示“正在收尾”，完成事实由协调器发布。关闭浮窗是显示行为，不暗中改变前后台位置；停止是任务命令，两者必须区分。

不打扰模式不是另一种权限授权：原本需要确认的动作仍需要确认。首版不新增多个并行 Agent、多个后台任务或多屏工作台。

## 6. 中途输出：提高可见性，不制造刷屏

用户已确认将每个模型 function 调用的 `commentary` 改为必填；候选版已接入非空和长度预检。这里的整体 batch 工具本身算一次调用，不要求内部每个点击分别说明。

已确认目标：**每个模型 function 调用在执行前都有一句面向用户的简短意图说明**。一个响应若包含多个独立调用，每个都需说明；`android_computer` 的 actions 整体只需一句。不新增执行批次引擎。

例：“找到项目群并打开”“读取这一页，确认预约时间”“列表更新了，按群名重新定位”。避免“调用 android_ui”“执行操作”这类无信息句，也不要求输出隐藏推理过程。

显示分为三层：

- **胶囊**：当前一句说明，随当前批次更新。
- **最新说明保留**：开始下一模型步骤或等待响应时不清空；直到新的说明到来才替换。前后台使用相同实时投影，后台胶囊不停止更新。胶囊展示最多两行，完整说明及过程通过独立展开入口读取，后台正文点击切前台的语义保留。
- **Chat**：正常 Agent 消息气泡，按既有消息/工具身份避免重复插入；保留跨轮可读的过程。
- **详细日志**：完整工具名称、参数、结果、耗时和错误，继续使用原有统一轨迹。

模型意图不等于执行结果。说明可以写“正在打开项目群”，只有真实结果后才显示“已打开”；失败和未执行必须由工具事实明确呈现。网络连接、重试、暂停生效和迁移中的提示来自系统真实状态，不能要求模型在网络断开或思考尚未返回时持续生成文字。

必填字段本身不保证实时：若当前请求整包返回，用户仍要等模型完成本次响应才能看到它。后续如接流式，只有完整可识别的展示文本可提前显示，执行仍等待完整参数与全批次预检；不能拿半截参数执行。

建议按批次校验有效、非空且有长度上限的说明，并在明确缺失时于副作用前返回有界纠正结果。不能因文案不理想自动重试已经执行的工具，不能为了补一句说明多开模型任务，也不能伪造“模型说了什么”。服务端 web/code 的进度按各自真实事件展示，不强行套手机 function 参数。

取消、失败、迟到输出都带 runId/callId/批次身份，不能污染新任务或重复进 Chat。短说明增加的 token 应与减少重复观察等收益分开测量，不预先承诺更便宜或更快。

## 7. 集成与验收

- 协调器独占切换命令接纳、操作门禁、暂停与恢复决定；显示会话后端拥有资源和真实迁移回执。UI 无设备执行权限。
- 暂时的“切换中”是协调器管理的操作状态，不是第二个任务生命周期。禁止再加一个悬浮窗本地运行状态机。
- 用户请求可扩展现有类型化控制命令，经既有统一设备操作入口串行处理，不伪装成模型工具调用，不新增旁路 shell 或任意脚本能力。
- 后台无障碍未验收时不能复用主屏默认窗口冒充后台 UI 树。模型应得到真实能力信息，必要时使用绑定后台显示屏的截图/坐标能力。
- 验收前台→后台→前台多次往返、暂停/停止抢占、迟到响应、人工交互、任务归属、Activity 重建、输入法与节点失效；逐项确认状态保留和主屏无意外操作。
- 验收说明缺失、批次多调用、失败、重复消息、取消与网络重试。只读观察和工具轨迹不得新增截图或重放。

前后台运行中任意切换是本轮新增的产品要求；此前“只在启动时选择”的设计限制被本草案替代。双向迁移的技术实现和完整实机验证仍是交付前提，现阶段不能将正常退出的单向迁移结果直接冒充全部已完成。
